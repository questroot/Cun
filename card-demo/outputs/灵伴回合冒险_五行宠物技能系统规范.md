# 灵伴回合冒险：五行、宠物与技能配置规范

> 2026-10-04 · 迭代草案。以用户本次文字说明为准；参考截图尚未可靠解析，截图中的具体技能数值/触发条件不作为已确认需求。本文不宣称未实现功能已经可用。

## 本次需求与现状

- 目标：五只宠物对应金、木、水、火、土，可继续增加宠物；每宠物固定 1 主动、4 被动，主动/被动可附加状态或引发追打。主角能切换物种属性，并自由组合 1 主动、4 被动。
- 已确认编队：`hero` 主角固定上阵，`sprout` 木、`ember` 火、`pebble` 土、`mist` 水、`metal` 金（金犼，物种金毛犼）五只宠物中选四只，共五名我方单位；九宫格容量不变。新宠物由 `units.json` 的 `playable: true` 进入候选库，不在程序名单中写死。
- 当前可直接改的配置：在 `data/units.json` 的宠物条目修改生命、攻击、防御、速度、暴击、`elements`、`skills`（恰好一个主动 ID）、`passives`（四个被动 ID）、`chase`（旧追打字段）、`portrait`（可选资源路径）；具体主动消耗、倍率、附加效果到 `data/skills.json` 查该 ID 修改；被动触发、效果、时长和数值到 `data/passives.json` 修改；五行关系和倍率到 `data/rules.json` 修改。主角当前存档仍只有 `hero_skill`；`skills.apply` 目前只支持单状态。保存 JSON 后重启游戏生效，务必保证被引用的技能 ID 存在。当前暂未提供图形化策划编辑器或多效果解释器。
- 金犼（物种金毛犼）已使用独立透明角色贴图 `portrait: res://assets/characters/pet_metal.png`，编队、宠物背包和战斗共用此贴图；岩球仍使用自己的资源。显示名与物种分别读取 `name`、`species`，内部 ID `metal` 不变以兼容旧存档。当前是静态二维角色素材与既有程序动作，并非可编辑三维模型或多帧骨骼动画。

## 五行及伤害（第一阶段已接入）

- 属性 ID 使用 `metal` 金、`wood` 木、`water` 水、`fire` 火、`earth` 土。`units.json` 的 `elements` 为数组；当前只用第一个值计算。`skills.json` 的 `element: "owner"` 表示由施法者当前属性决定，也可为固定属性 ID；基本攻击未指定时仍按施法者属性判定。
- 克制：金克木、木克土、土克水、水克火、火克金。攻击属性克目标首属性乘 `element_advantage`（暂定 1.25）；受目标首属性克乘 `element_disadvantage`（暂定 0.8）；其余乘 1。系数由 `rules.json` 调整，不是最终平衡值。元素倍数在现有基础伤害/防御公式后、暴击与护盾前结算。
- 将来双属性要先确认攻击属性如何选择、多属性防御如何聚合（取最强、最弱或乘积）以及同一对同时克制/被克时的优先级；不能把数组直接全乘。

## 技能配置目标结构（后续阶段，尚未接入）

- 单位模板：`elements: ["wood"]`、`active_skill: "sprout_burst"`、`passive_skills: ["p1", "p2", "p3", "p4"]`；主角技能库（可选列表）与装备槽位分离，存档中的 `hero_loadout: {"element":"wood", "active":"...", "passives":[...]}` 只保存已装备 ID。原存档 `hero_skill` 需迁移而不抹除进度。
- 单条技能建议以 ID 引用数据：`kind`（active/passive）、`power`、`cost`、`cooldown`、`target`、`trigger`、`effects[]`。效果数组每项包含 `kind`、`target`、`status` 或 `stat`、`value`、`duration`、`chance`，追打另设 `chase_on` 与 `chase_limit`；不把视觉动画 ID 和逻辑状态 ID 混用。
- 普通宠物伤害按自身属性；主角主动/被动伤害按当前选择的属性（除非技能明示固定属性）。所有技能效果必须先经过配置验证（技能 ID、槽位数、目标、数值、触发链）再进入战斗。
- 本次“技能编辑器”已明确为**策划能灵活修改宠物技能配置，而不是在代码中为每宠写死效果**；当前使用 `data/units.json` 指向 `data/skills.json` 和 `data/passives.json`：每只可选宠物 1 个 `skills` ID、4 个 `passives` ID。`passives.json` 的 `trigger/effect/duration/value` 决定效果，不按槽位限制类型。目前解释器只支持 `heal`、`shield` 和已有 `damage_up` 等单效果，追打仍是旧 `chase` 独立字段，新增状态/多效果尚未接入，不能仅填写新字段就期望战斗生效。后续应对 JSON 添加启动校验及多效果执行器。

## 状态词汇及追打约束

- 可触发追打的状态：小浮空、大浮空、倒地、击退、定身、高连击；建议规范 ID：`air_small`、`air_large`、`knockdown`、`knockback`、`root`、`high_combo`。
- 其他状态：中毒 `poison`、点燃 `burn`、目盲 `blind`、混乱 `confusion`、标记 `mark`、麻痹 `paralysis`、沉默 `silence`、睡眠 `sleep`。这 8 类默认**不能单独触发追打**，但可由追打技能附加。
- BUFF/DEBUFF 属性：生命、攻击、防御、破甲、命中等，应区分最大生命与当前生命、百分比与固定值、加成与减益、叠层/刷新/清除时机。生命扣减和治疗不应混成属性增益。
- 兼容旧 `air` → 小浮空、`down` → 倒地；旧 `stun` 与“定身/麻痹/睡眠/沉默”的效果不等价，不能直接改名。旧 `damage_up` 用在目标身上时会使目标出手增伤，`mist_arc` 现有“易伤”语义需单独修复并测试。具体控制效果（定身是否禁止主动技能、睡眠受击是否醒来等）和状态持续时点需确认。
- 追打链条需要记录已经追打的单位、最大段数和当前触发状态；不能让同一个被动递归无限追打。被动造成状态时是否即时开启新链须明确；现有代码仅在主动命中的 `air/down` 开启链。

## 分阶段实施与验收

1. **已做基础接入**：现有单位五行数据、规则关系与伤害倍率；未改变当前编队及技能选择方式。既有技能仍保持原释放流程。
2. **当前阶段已接入（引擎回归待测）**：金犼在配置中拥有 `metal_edge` 主动和 `metal_edgeguard/metal_mend/metal_focus/metal_ward` 四个暂定被动，编队页可从五宠中选四宠，存档保存上阵角色，未上阵宠物的等级与经验也可保留；旧有四宠队伍保持原样。数值和效果均可在 JSON 修改。当前这四个被动为原解释器支持的护盾/治疗/增伤，并非完整新状态技能系统。
3. **第三阶段**：统一效果执行器、14 状态与 6 种追打触发、四个被动槽位、主角元素/技能装备 UI；为控制、护盾、轮末状态和旧档分别补确定性测试。
4. **第四阶段**：技能视觉/音效绑定与实际编辑体验，再根据五宠美术确认更新旧美术需求文档；逐一进行独立场景和主流程验证。

## 开发与交付验收规范

- **每次新增功能或修复问题，交付前必须运行 Godot 全项目冒烟测试，且结果为 `SMOKE RESULT: PASS (0 failed)`；未通过则继续修复，不得标注完成。** 测试入口：`scripts/tests/smoke_test.gd`，使用 Godot 4.7.2 控制台版以 `--headless --path <项目目录> --script res://scripts/tests/smoke_test.gd` 执行。
- 新功能要在冒烟测试中补对应断言：正常数据、空数据/缺失技能，以及涉及 UI 遮挡时的绘制层级。仅静态检查 JSON 或“能打开场景”不等于通过验收。
- 宠物背包绘制在世界角色和 NPC 上方；主城角色按脚底 y 值设置 `z_index`，背包层级必须更高。打开背包时验证人物不会覆盖面板，关闭后验证原有主城功能仍正常。
- 无头冒烟测试不能代替实机画面检查；界面改动还应在 Godot 编辑器或运行窗口观察布局，尤其检查缩放和窗口尺寸。若实机视觉检查未完成，交付时须明确说明。
