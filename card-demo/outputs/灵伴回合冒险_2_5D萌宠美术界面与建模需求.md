# 《灵伴回合冒险》2.5D 萌宠风格美术、界面与建模需求

> 版本：V1.0 · 2026-10-04　｜　用途：美术立项 / 外包发包 / 程序接入验收
> 依据：当前 Godot 项目的实际入口、场景、数据与脚本；本文是**未来美术制作需求**，并不表示相应素材已经完成。

## 1. 项目基线与不可误读的边界

- **当前正式启动入口**为 `scenes/MainCity.tscn`，1280 × 720 设计视口，Godot 4.7 项目配置、Compatibility 渲染。启动直达主城，不以旧 `MainMenu.tscn` 作为主流程入口。
- **当前正式主城**是 `Control + Node2D` 绘制的俯视 2.5D 地图，地图世界约 2080 × 940；建筑、地面、花园使用程序绘制；角色/NPC 使用 2D 绘制、脚底定位、纵深缩放与 Y 向排序。**不要把已有 `City3D.tscn`、`.glb` 建筑和概念整图误认作当前运行中的主城**：这些是历史探索/参考资源，本轮必须以 `MainCity.tscn` 的俯视 2.5D 玩法为准。
- 当前流程：主城 WASD / 点击移动 → 靠近关卡向导、按 E 或点击交谈 → “查看关卡” → 三关选择 → 3 × 3 阵位编队 → 回合战斗 → 结算回主城；主城东出口还通往可探索的“云庭外缘”，可返回主城。主城的“调整阵容”也可直接进入编队页。
- 当前战斗是 **2D 角色 + 三路九宫格**：我方五名单位（旅者和四只灵伴）、敌方四名，包含普通攻击、奥义、状态、追打连击、血量、能量、行动顺序和胜负弹窗。此轮的“建模”是为**俯视 2.5D 视觉生产、渲染烘焙及后续扩展**服务，不要求把运行时战斗/主城改造成实时 3D。
- **运行时更新（2026-10-04）**：主城/外缘/战斗角色及编队头像已改用 `assets/characters/pet_*.png`，战斗按关使用 `assets/backgrounds/battle_stage_1/2/3.png`，界面背景为 `menu_pet_garden.png`，特效为 `assets/fx/fx_pet_atlas.png`。历史旧图集、旧背景和建筑 GLB 与新运行素材应严格区分。项目当前未发现自带字体或音频素材，文字依赖 Godot 默认字体；字体选型与音效/BGM 如纳入本期，需另行明确。

## 2. 视觉方向：暖心云庭 × 轻奇幻萌宠

**关键词**：俯视童话庭院、圆润有生命力、温暖探索、小体量奇幻、清晰的战斗反馈。目标观感为“可亲近的萌宠冒险”，不是写实暗黑、厚重仙侠，也不是像素风。

- **统一透视**：主城采用从上往下观察、能看到屋顶与少量正立面的 2.5D 正交/弱透视语言；道路、门阶、屋檐、树冠与脚底接触点遵循同一投影规则。禁止在同一画面混入地平线侧视背景、夸张广角建筑或三维模型截图直接拼贴。
- **造型比例**：灵伴头身比偏 Q、主体大而四肢短；一眼看出芽叶、火苗、岩块、狐耳/雾尾等识别点。旅者与向导约 2.5–3 头身，脸部表情清晰但不依赖细密线条。敌我同物种可共享基础轮廓，以颜色、纹样与附饰区分，避免仅靠色相识别。
- **材质**：绒毛/叶片/软陶/磨圆石/半透明雾气的“玩具感”混合；边缘柔和、适度 AO 与接地阴影，避免金属重反射和过度泛光。场景细节优先投放在可辨识轮廓、门与路标，平铺地面降低对比度。
- **色彩基准（建议，待首轮色板确认）**：主城玉绿 `#497D69`、暖石 `#DBC9A5`、深青 `#315D55`；强调金 `#F3D591`；芽灵绿 `#68BA76`、焰团橙 `#F49A63`、岩球褐 `#BA9B79`、雾狐青蓝 `#87B9CA`、旅者蓝 `#537BD9`。最终必须用实机截图校色；对敌方增加剪影/标识差异。
- **层级**：地面 → 地面装饰/投影 → 建筑/障碍与角色按接触点排序 → 前景树冠/遮挡 → HUD/对话。交互目标的轮廓与选中态应压过背景细节。角色落地影与所有可行走地面保持一致。

## 3. 场景与环境资源清单

### 3.1 云庭主城（P0）

当前地图的建筑/障碍脚印由 `city_map.gd` 的 `OBSTACLES` 控制；**视觉底座必须对齐碰撞与寻路**，不能让美术门口看起来可走而代码禁止通行。2026-10-04 已依据实机截图把建筑/喷泉/花坛的宽矩形缩为地面接触核心脚印，屋檐、阴影和周边铺装不再整块挡路；右上城门另设向北引道与传送区。可制作分层 2D 原画、由低模渲染烘焙的分层图、或可拆的轻量模型源文件；运行时优先用分层 2D 素材接入现有 Node2D。

| 资产组 | 数量/内容 | 设计要求 | 现有脚印/功能 |
|---|---|---|---|
| 地面基底 | 1 套，可平铺草地、主路、石砖、广场 | 俯视屋顶方向一致；边缘可拼接；不压住目标/UI | 世界约 2080 × 940；道路连通两处广场 |
| 主要建筑 | 5 座：西厅、集市、东厅、档案馆、观测塔 | 至少区分屋顶形状、入口和功能符号；屋檐分前后层 | 障碍索引 0/1/2/6/7，详见 `city_map.gd` |
| 公共景物 | 1 座喷泉、4 片花园、树与灯柱组合 | 喷泉可轻动效，花园轮廓不误导寻路 | 障碍索引 3/4/5/8/9 |
| 导航入口 | 画面右上实际城门 1 处、与道路连接的通行引道 | 角色走至门洞下沿切换云庭外缘；不把东南角误作出口 | `EXIT_REGIONS` 区域 x=1919–1959、y=447–474；上行引道由 `GATE_APPROACH` 控制 |
| 氛围装饰 | 叶片、花瓣、云纹、灯火等 1 套 | 分离前景/中景，重复不显机械；优先支持关闭/降级 | 不新增隐形障碍 |

**关键对齐数据**：`city_map.gd` 世界管理边界 `BOUNDS=Rect2(64,300,1952,530)`；实际可行走的石路与广场为 `WALKABLE_AREA=Rect2(70,450,1940,365)`，城门引道为 `GATE_APPROACH=Rect2(1880,430,100,180)`，玩家脚底按半径 16 像素内缩并避开 `OBSTACLES`；两个连通区域不应被误当成一整块不可走草地。主城 `NPC_FOOT=(843,562)`，玩家默认脚底 `(334,558)`；这些数字是当前程序空间坐标，不代表建议原画裁切尺寸。建筑形体/阴影可外溢，但**接触脚印、门前通路与障碍矩形**必须以该脚本为准。UI 不应遮挡中央向导、主通路及东侧出口。

### 3.2 云庭外缘（P1）

制作与主城同色系的草坡、石路、树丛和左侧返城门；当前是 1280 × 720 固定探索区域，主角同款俯视行走形象可复用。它目前是小型联通探索区，**不要写成已完成的开放世界、采集或多 NPC 剧情地图**。

### 3.3 三个关卡与战斗舞台（P0/P1）

数据中只有三关：`stage_1 晨光草地`、`stage_2 碎石小径`、`stage_3 薄雾林缘`。关卡页各需 1 张缩略插画/图标；战斗场景建议交付 3 张同一镜头语言的可替换分层舞台（首阶段 P0 可先完成“晨光草地”，其余 P1）。当前代码仅加载同一张 `battle_garden.png`，**逐关背景切换属于接入任务，而非现成能力**。舞台中轴及双方九宫格角色区域应留白，避免高对比装饰影响技能阅读。

## 4. 角色与萌宠资源清单

| ID / 名称 | 阵营/现状 | 视觉母题及最小识别点 | 建议制作优先级 |
|---|---|---|---|
| `hero` 旅者 | 我方固定上阵，主城玩家 | 轻便旅装、披肩/围巾、圆脸、冒险标志；与四宠体量协调 | P0 |
| `sprout` 芽灵 | 我方灵伴 | 叶芽双冠、鲜绿软团；技能“藤蔓牵引” | P0 |
| `ember` 焰团 | 我方灵伴 | 温暖火苗冠、橘色圆体；技能“焰火喷射” | P0 |
| `pebble` 岩球 | 我方灵伴 | 层叠圆石/岩盾、小短肢；技能“岩盾冲撞” | P0 |

| `metal` 金犼（物种：金毛犼） | 我方第五只候选灵伴，选四上阵 | 金色鬃毛、幼狮般圆脸、短肢、额间玉金饰；区别岩球的层叠石质轮廓；技能“金芒突刺” | P0；独立透明静态素材已接入 |
| `enemy_seed/flame/stone/wisp` | 四种敌方野生变体 | 复用对应物种骨架/基础模型；野生纹样、眼神或饰片、阵营边框明确区分 | P0 |

**形态与动作**：主城角色至少准备待机、四向行走、转向、交互；战斗至少准备待机、普通攻击、奥义蓄力/释放、受击、倒地/退场、追打。若采用 3D 建模烘焙为 2D，则以统一正交镜头、固定光照/比例输出透明序列或骨骼动画；当前战斗双方朝向相对，左右镜像时不对称纹样/文字不得被错误反转。`battle_actor.gd` 当前角色是代码矢量绘制并用 Tween 演出，这一部分替换需要程序单独接入，不能仅替换图集就宣称战斗角色升级完成。

**表情与剪影验收**：在战斗实际缩放下，四只宠物与旅者不借助名称也能认出；同物种敌我在灰度截图中仍可借助轮廓/配件/UI 阵营标识区分；受击与技能前摇的姿势变化清楚。

## 5. UI / UX 美术需求

1. **主城 HUD（P0）**：左上“云庭主城·漫游”标题、等级/历练进度/队员数量；右上“调整阵容”；底部移动与向导提示。为原本深青+金边卡片提供统一 9-slice 面板、按钮、导航图标与状态徽记。关卡向导的点击热区/名称牌要与形象对齐，近身“按 E”提示区别于可点击标识。
2. **向导对话（P0）**：保留“查看关卡”和“稍后再说”两个决策，突出第一按钮但避免误点；对话时暂停角色移动。底部对话框不要压住关键按钮，头像/立绘可作为可选拓展。
3. **关卡选择（P0）**：三张主题卡，对已解锁/未解锁/悬停/按下/键盘焦点给出不同形态；明确经验奖励与“进入编队”。锁定态要同时用锁标、文案和灰阶/边框区分，不能只改颜色。返回主城固定可见。
4. **编队（P0）**：名单中五人头像、3 × 3 阵位、前/中/后排与上/中/下三路、选中/拖拽目标/可交换态、主角奥义下拉框、保存与开战按钮；格子空位不可和禁用态混淆。主角必须上阵且共五人，错误提示醒目。布局不能让头像缩放失真。
5. **战斗（P0）**：顶部回合与行动顺序；两侧角色位置、九宫格状态条、血量和能量；底部普通攻击/奥义/战斗日志；技能名、追打连击、伤害飘字、胜负结算。状态“浮空/倒地/眩晕/护盾/易伤”需不同图形符号与文字标签；能量不足和 CD 状态应可识别。颜色不是唯一信息载体。
6. **外缘与全局弹窗（P1）**：外缘返回提示、通用确认/错误/胜败弹窗与主城同一组件规范；不要为了美术改造改变按钮触发结果。

**排版与适配**：以 1280 × 720 为基准，重点检查 16:9 窗口缩放及较窄窗口不遮挡功能按钮；安全边距建议 ≥ 24 px，正文/按钮文字通常 ≥ 16 px，关键按钮可点区域建议 ≥ 44 × 44 px。实测简体中文字体字重、数字宽度与图标对齐；提供普通、悬停、按下、焦点、禁用五态，适配鼠标和键盘焦点。

## 6. 技能特效及反馈制作

- `hero_strike` 疾风突袭：短弧形风刃、快速位移、浮空符号；`hero_wave` 震荡波：低位冲击环/倒地符号；`hero_guard` 守护誓言：护盾壳与持续护盾标识。
- `sprout_burst` 藤蔓牵引：叶藤上扬/浮空；`ember_flare` 焰火喷射：暖橘火束/倒地；`pebble_ram` 岩盾冲撞：低重心石屑/眩晕；`mist_arc` 雾刃：青蓝弧光/易伤标识。敌方 `enemy_burst` 可复用基础猛击并随物种换色；空中/倒地追打要有独立提示。
- 分离蓄力、命中、消散帧/轨道；镜头轻推与短闪只辅助阅读，不遮蔽血条。尊重低闪烁需求：提供弱闪/关闭震屏方案。伤害、护盾和连击的视觉出现时机要与程序结算信号对齐。
- 现运行时使用 `assets/fx/fx_pet_atlas.png` 统一法术图形；如进一步细化成套技能动画，应提供透明背景、效果图集索引和每个状态的触发说明。

## 7. 建模与资源交付技术规范

### 7.1 推荐生产链

- **优先方案**：原始可编辑 3D 低模/中模（角色、建筑） → 统一正交镜头渲染 → 分层透明 PNG/WebP 或序列帧 → Godot 2D 节点集成。保留源模型方便统一改色、补方向和重烘焙；地图道路与遮挡使用分层 2D，运行时无需实时 GLB。
- **可选方案**：直接绘制 2D 分层角色/场景并交付源工程；满足同样的方向、尺寸、脚底锚点与动画帧规范即可。仅在后续明确重新启用真实 3D 主城时，再单独立项 GLB 实时接入、碰撞、光照和相机参数；**不能用历史 3D 场景替换当前入口**。
- 建筑源模型按五栋独立命名；枢轴置地面中心，门面方向一致；导出 `glb` 可作为源资产/预览，但须同时交付符合当前二维坐标的渲染切片、遮挡掩码与接触脚印图。喷泉/树/灯按模块化组合供复用。

### 7.2 文件、坐标、图集与源文件

| 类型 | 交付要求 |
|---|---|
| 场景分层 | 地面、建筑后层、建筑前景遮挡、装饰、碰撞脚印参考图分别导出；场景原点与现有世界坐标一一对应；边缘不得出现原图背景或烘焙天空。 |
| 角色 | 独立透明素材/动画；标注角色 ID、方向、动作、帧率、中心轴和**脚底锚点**；主城与外缘共用玩家源资产，战斗可采用更强调动作的同设定表现。 |
| UI | 矢量源文件或可编辑分层源文件，导出 PNG/SVG（以 Godot 实测兼容为准）；九宫格拉伸面板提供边距参数与状态表，图标提供语义命名。 |
| 技能 | 按技能 ID 对应文件/图集帧区；透明背景、Blend 建议、前摇/命中/消散时序与层级标注。 |
| 命名 | `city_<area>_<layer>_v01`、`unit_<id>_<action>_<dir>_v01`、`ui_<page>_<element>_<state>_v01`、`fx_<skill_id>_<phase>_v01`，避免纯中文或无版本的覆盖式命名。 |
| 导出 | 推荐 sRGB、透明 PNG（避免预乘边黑）、常规图标可 SVG；纹理不强制全部做成大图，按 Godot 导入、纹理页和内存预算复核。源文件与导出文件均交付，并记录许可证/来源。 |

> 具体角色帧尺寸、模型面数和纹理上限应在**P0 风格试片实机验收后**按画面占比及目标平台锁定；这里不臆造尚未确定的性能预算。若沿用当前 `sprite_atlas.gd` 接口，先确认 `unit_atlas.png` 的实际排布及裁切代码，**不要仅按“128 × 128 格”假设直接覆盖图片**；角色主展示与战斗角色的接入路径不同。

## 8. 制作顺序、验收与分工
