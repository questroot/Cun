# 小团队协作指南

## 角色随任务切换

每项任务约定一位推进者和一位检查者，可以轮换，不是固定职位。涉及方向、成本、资产授权或不可逆变化，由用户与伙伴共同确认；未得到授权的事项标记“待确认”，不把沉默当批准。

## 从一个小任务到合并

1. 写一句目标、可操作的完成判据、负责人与涉及目录；有未知机制时先用[实验模板](templates/experiment.md)。
2. 从最新主分支建短分支，一次只解决一个问题。优先让每个 PR 能独立理解、试玩与回退；不要混入无关格式化或架构重写。
3. 开始前告知对方将改哪些场景、资源或大文件；范围重叠时先分开任务或约定先后顺序。
4. 提交前自查差异；记录实际测试环境、步骤、结果和未测项。未运行只能写“未验证”，不能写“通过”。
5. PR 由另一人检查目标、影响、证据与授权边界。意见未解决时明确保留或等待，不伪称审核完成。
6. 合并后按 PR 操作路径再检查一次。发现回归先回退或缩小修复，不借机重构整套工程。

合并权限和分支保护尚待确认；仓库提供基础工具测试和资源检查工作流，需推送后确认 Actions 结果。这些约定不意味着 GitHub 已配置强制审核或分支保护。

## 二进制与场景冲突

- 美术、音频等二进制文件同一时间由一人编辑。先在沟通渠道报“文件路径 + 编辑者 + 预计释放时间”，结束后通知；不假定已有 Git LFS 或文件锁服务。
- 文本场景也可能产生语义冲突，尽量拆分编辑范围。冲突出现时由双方确认保留版本，不用“一律 ours/theirs”处理。
- 原始素材与导出资源关系要清楚；不把缓存或临时导出混入提交。生成资源重新导入后，实机确认引用、外观和声音，不仅确认 Git 能合并。
- 大资源加入前共同确认存储方式、体积与授权，未确认不引入新基础设施。

## 任务完成判据

任务开始时从下列检查中选择适用项；无需每个任务强行套齐。

- 目标操作能在指定环境完成，核心结果与失败路径符合预期。
- 受影响场景、交互和内容引用经过实际验证；记录引擎/版本、平台与步骤。
- 改数据或存档时验证对应版本边界，不能只测新建状态。
- PR 没有无关修改、未知来源资源或泄露信息；另一人已检查，遗留问题有明确后续处理。
- 纯文档任务检查事实、相对链接和写入范围；不以此冒充玩法验证。

缺少适用测试证据时，状态是“实现完成，验收待做”，不是已验收。

## 授权边界

目前无 LICENSE，许可、商业用途、署名、作品归属和分发范围均待确认。本文档不授予开源许可，也不代表成员可以自由商用或再分发。

引入第三方素材、字体、音乐或代码前记录来源、许可文本/凭证、署名要求及使用范围；来源或授权不明确的资源先不合入。发布、收费、外包、授权声明、对外分享仓库与改变项目许可需要另行确认。已获授权的实验也不自动包含上述授权。

方向或长期技术取舍用[决策模板](templates/decision.md)保留确认者和状态；未确认项可以继续讨论，不写成既定规则。
