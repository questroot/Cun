# 轻量架构边界

目标是让小团队能独立推进、合并后可试玩，而不是提前搭建框架。正式游戏方向、正式引擎、首发平台和工程位置均待确认；**当前明确任务是为现有 Godot 原型提供 Windows 启动器、架构与文档维护规划，并由有权限的负责人处理 GitHub 交付**，不是授权实现候选新玩法。

本文区分三类信息：**现有**是已读取的配置/源码事实，不等于实机通过；**本次新增**是当前任务的交付边界，落地与测试结果以[共享现状](../PROJECT_STATUS.md)和实际源码为准；**未来建议**须另行批准，不宣称已实现。文档维护约定见[文档规划](documentation-plan.md)。

## 当前层次与调用关系

| 层 / 模块 | 现有事实或本次边界 | 不应越过的职责 |
| --- | --- | --- |
| Windows 入口（本次新增） | 根 `Launch.cmd` 调用 `launcher/Launcher.ps1`；Windows PowerShell 5.1 WPF GUI | 不修改原型入口、玩法或默认创建新项目 |
| 启动器界面（本次新增） | 收集 Godot 选择和 game/editor 操作，展示诊断与文档入口；调用 `launcher/Launcher.Core.ps1` | 不复制核心探测规则，不代替共享状态或游戏验收 |
| 启动器核心（本次新增） | 选择/探测 Godot、内置压缩包校验解压、实际版本检测、启动 game/editor、诊断及本机快照；本机配置/日志/快照写入 `.local/` 忽略目录 | 不联网、不调用运行时 LLM、不改 Godot 配置/游戏存档、不推送 GitHub |
| Godot 原型入口（现有） | [项目配置](../card-demo/project.godot#L9-L34)：`config_version=5`，入口 `MainCity.tscn`，标记 `4.7` / `GL Compatibility`，四个 Autoload | 配置标记不能证明本机版本、兼容性或运行成功 |
| 场景与表现（现有） | [主城](../card-demo/scripts/scenes/main_city.gd#L1-L9)是 Control/2.5D 交互；[场景路由](../card-demo/scripts/managers/game_manager.gd#L9-L32)按场景名切换并关闭弹窗 | 已有 3D 实验不是默认流程，也不是新方向决策 |
| 规则与战斗（现有） | [战斗管理器](../card-demo/scripts/managers/battle_manager.gd#L1-L80)管理单位/队列/行动序号；[行动流程](../card-demo/scripts/managers/battle_manager.gd#L104-L129)中我方等待玩家、敌方自动 | 不误称已实现候选自动战斗/远征；演出回执不能变成另一套伤害结算 |
| 数据与持久化（现有） | [数据管理器](../card-demo/scripts/managers/data_manager.gd#L5-L27)加载 JSON 表并返回深拷贝，使用 `user://spirit_save.json`；[写档](../card-demo/scripts/managers/data_manager.gd#L128-L136)发送 `save_changed` | 游戏存档与启动器 `.local/` 配置各自独立 |
| 文档与事实（现有 + 本次新增） | [文档导航](README.md)承载入口；共享现状由负责人维护；启动器打开/刷新生成 `.local/project-snapshot.md` | 自动快照不能批准方向、自动宣布通过或覆盖人工正典 |

```text
Launch.cmd → Launcher.ps1（WPF）→ Launcher.Core.ps1
                                  ├─ Godot 可执行文件 --version / 诊断
                                  ├─ game: 后台 --headless --editor --import → 错误/缓存门禁
                                  │         → --path card-demo → project.godot → MainCity
                                  ├─ editor: --editor --path card-demo
                                  └─ .local/ 配置、日志、project-snapshot.md

Godot 场景 → GameManager（路由 / 关卡状态）→ DataManager（表 / 单机存档）
战斗场景 ↔ BattleManager（规则 / 行动与演出回执）→ DataManager
GameManager → UIManager（关闭弹窗）；场景订阅 DataManager.save_changed
共享现状 / 相关规格 → 人工工作核对；源码与配置 → 本机快照摘要
```

启动模式参数是调用语义，实际参数构造、引用处理、探测优先级、函数名和返回字段以核心实现为准，不由本文虚构。入口以仓库相对位置定位项目，不把开发者绝对路径写成团队默认配置；引擎路径属于本机设置。用户明确要求随仓库分发Godot，采用[86MB压缩包与许可/校验清单](../.setup/Godot/README.md)，需要时解压到 `.local/godot/`，不提交超限裸exe，不联网更新。原型没有通过启动器变成启动器的代码依赖。

## 实施阶段与依赖门禁

1. **基线核对（本次）**：读取共享现状、配置与相关规格，确认原型入口及任务权限；不以文档齐全代替运行。缺 Godot 时记录实际缺口，继续不依赖引擎的文档工作。
2. **启动器核心 → GUI（本次）**：核心先明确探测、版本、启动失败与本机写入边界，界面调用同一逻辑；配置/日志/快照不进入共享源码。测试证据区分核心检查、GUI 交互、实际 Godot 进程启动。
3. **文档核对 → GitHub 交付（本次、负责人操作）**：功能与测试的事实进入共享现状，核受影响文档、相对链接与隐私，再按授权检查差异、提交/推送。没有提交/远端证据不写“已上传”；本文维护者不自动获得 git 写权限。
4. **方向决策 → 新工程基线（未来）**：先确认玩法、输入/视角、引擎、目录、存档隔离与资源许可，再选择最小复用。参考[候选首个可玩计划](design/first-playable.md)，不当作已批准排期。
5. **机制实验 → 可玩闭环（未来）**：按获批路线验证战斗，再接探索/当局数据/结算，最后扩内容；不得由启动器任务直接跨入候选实现。

阶段依赖是完成条件，不是工期承诺。每阶段记录已验证范围、失败和未验证项；引擎启动、GUI 可见、完整玩法走通、GitHub 发布是不同验收层次。

## 当前接口与版本边界

- **启动器 ↔ Godot 进程**：输入为本机引擎、项目目录和明确的 game/editor 模式；版本检测与启动分别处理错误。诊断需区分配置声明、实际版本、发现/启动状态及失败原因。只创建进程不证明窗口正确显示、玩法正常或旧档兼容。
- **GUI ↔ 核心**：界面发出明确操作，核心负责探测与进程/本机文件处理；错误需展示给用户，不用成功提示掩盖失败。当前新增[核心源码](../launcher/Launcher.Core.ps1)已可静态核对：`Get-CunPaths` 返回项目/本机文件路径；`Get-CunEngineInfo` 返回 `Ready` / `Version` / `Message`；`Start-CunProject` 返回进程与输出任务，`Write-CunSnapshot` 返回快照路径。界面须区分未就绪、进程启动和游戏验收，函数/字段改变时同步核调用方。本次不预设远程 API、服务或公共 SDK；源码存在仍不等于测试通过。
- **场景 ↔ 战斗**：[信号定义](../card-demo/scripts/managers/battle_manager.gd#L3-L13)包含行动开始/命中/动画完成等信息；行动序号和阶段用于演出回执。[UIManager](../card-demo/scripts/managers/ui_manager.gd#L5-L57)仅管弹窗；当前不是严格纯规则层，未来拆分须有实需。
- **数据 ↔ 存档**：当前[读档与兼容分支](../card-demo/scripts/managers/data_manager.gd#L29-L89)存在旧阵容/阵位兼容；尚不能据此宣称通用迁移框架。下文 `schema_version` / `save_version` 是未来建议，本次不改数据或旧档。
- **启动器配置 / 快照**：与 Godot 的 `config_version`、游戏数据版本、存档版本相互独立。当前[核心设置读写](../launcher/Launcher.Core.ps1#L27-L49)使用 `.local/launcher.settings.json`，字段为 `version = 1` 与 `engine_path`；缺文件返回空引擎，格式/版本不符则记录诊断并要求重新选择，不改原型。未来改变字段语义须定义默认值或兼容策略，不能与 `save_version` 混用。当前快照是 Markdown 派生文本；若未来被程序消费，再定义快照格式版本，不宣称目前已有。
- **快照 ↔ 共享状态**：快照是打开/刷新时的本机观察，保留生成时点和未验证边界；不作为历史事件流、后台持续监听或验收凭证。共享现状的更新仍由执行者核事实后交给当前文件所有者。

## 原型与正式工程隔离

- [现有 Godot 原型](../card-demo/project.godot)保留原位，继续作为独立实验，不迁移、不自动升级、不直接作为正式工程模板。
- 新机制可先在授权范围内实验；正式方向确认后，再约定正式工程目录、引擎版本与首个可玩目标。
- 原型成果按“机制结论、数据、资源、代码”分别评估。引用机制结论不要求搬代码；复制任何资源或代码前检查依赖、来源与授权。
- 禁止正式工程隐式依赖原型内部目录。确需共享时，先约定所有者、格式和导入方式，再显式抽取最小内容。

## 按职责分开，按需要落地

| 边界 | 负责 | 尽量不负责 |
| --- | --- | --- |
| 规则与状态 | 游戏状态、合法操作、规则结果 | 直接播放音效、控制 UI 节点 |
| 交互与表现 | 输入转换、界面、动画、声音 | 复制一套规则或直接修改底层数据 |
| 内容数据 | 参数、关卡或实体定义及校验 | 把流程逻辑藏进无约束配置 |
| 平台与持久化 | 文件读写、设置、存档、平台适配 | 决定胜负或玩法规则 |

最初可以是少量文件或函数，不要求独立包、接口框架或固定目录。用一次明确的操作调用和返回结果连接规则与表现；需要多处响应时再引入事件。现有原型的 Autoload 不构成未来必须照搬的模块规范。

不强建 ECS、联网、依赖注入（DI）或插件系统。只有真实需求与可复现问题出现时，记录候选方案、成本与验收方法，再决定是否引入。

## 数据、资源、存档的版本各管各的

- **内容数据**：正式工程形成时选一个易编辑、可比较的格式；定义稳定 ID、必填字段、引用约束和 `schema_version`。加载失败给出具体条目与原因，不静默吞错。改 ID 或字段含义前检查引用。
- **资源**：使用稳定资源路径或 ID，写清源文件、导出文件、尺寸/采样等导入要求和授权来源。二进制不靠文本合并；替换前通知使用者，完成后在引擎内检查引用与显示/播放。当前用[资源清单和本地图册](../assets/README.md)管理制作信息；它不替代引擎导入器或游戏运行时加载器，暂不新建数据库服务。
- **存档**：与内容定义分开，只保存运行状态及必要内容 ID，不直接持久化引擎对象或节点路径。启用存档时再定义独立 `save_version`，校验读入并避免失败写入破坏旧档。
- 三者版本不必相等，也不与引擎版本绑成一个数字。PR 明确“是否影响旧数据、旧资源引用、旧存档”；不兼容时选迁移、拒绝加载或仅重置测试档，并获得受影响者确认，不能默认删除玩家数据。

## 每次跨边界变更的最小检查

1. 谁提供、谁读取，输入与失败结果是什么？
2. 是否改变已有内容 ID、资源路径或存档语义？
3. 能否通过一个真实操作路径验证，而不只看文件存在？
4. 改动可否局部回退？若不能，先写一份[短决策记录](templates/decision.md)。

引擎运行与旧档兼容均须实际验证；文档检查不能代替这些结果。
